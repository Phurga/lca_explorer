# Activity Browser and existing tools: research for the LCA viewer decision

Research date: 2026-10-03. Sources were checked live (PyPI JSON API, GitHub API, source of the AB `main` and `beta` branches cloned on that date, project docs). Items I could not verify are marked **[UNVERIFIED]**.

## Summary (5 lines)

1. AB 3 is **not stable**. It is a public beta (PyPI `3.0.0b202608291724`, 2026-08-29), built on Brightway 2.5 (`bw2data>=4.1`, `bw2calc>=2.0`, PySide6). The stable AB on conda-forge is still **2.11.2** (Brightway 2.4, PySide2).
2. AB 2 had a real plugin system (`ab_plugin_*` modules, `Plugin` class with `tabs`, conda-distributed). In the AB 3 beta that system is **gone**. What remains is a bare "import this Python package at startup" list, and the maintainers' own `AGENTS.md` says "Plugin architecture is being redesigned. Do not harden or invent a plugin API contract."
3. AB does embed QtWebEngine (Sankey, Graph Explorer, and a new D3 tree plot), so a web UI inside Qt is technically feasible.
4. **AB 3 beta already ships a SimaPro-style "Contribution Tree" tab** (lazy expand/collapse tree table with cumulative and direct impact bars, tier, a D3 partition/tree plot, plot-only aggregation by product/process/location/database, CSV/XLSX export). It was first committed on **2026-08-11**, so it is brand new and moving fast. This is the main competitor to what you plan to build.
5. Outside AB there is no maintained Brightway 2.5 process-tree viewer. `bw_graph_tools` (engine, active) and `brightwebapp` (Panel/Pyodide demo, active) are the closest. `bw2analyzer` is stale (last release 2023-09).

## Recommendation

**Build the standalone local web app (FastAPI + React) as the primary product. Do not build an AB plugin now.** Keep the backend as a clean Python library so an AB-embedded or AB-launched wrapper stays possible later.

Reasons:
- There is no stable plugin API to target in AB 3. Building on the AB 2 API means building on PySide2, Brightway 2.4 and a system the maintainers have already dropped. Building on the AB 3 "import a package" hook means guessing an API that is explicitly under redesign.
- AB 3 is beta, requires Python <3.13, pins `pyside6<6.10`, and pins `bw-functional==0b97` (PyPI already has `bw-functional 0.1.0`, released 2026-10-03). An AB-hosted plugin inherits all these pins and conflicts with your own dependency set.
- Your target users (practitioners) are likely to run AB 2.x (stable) for some time, and the AB 3 beta for others. A standalone app that reads the Brightway project directory works with both, as long as the Brightway project is 2.5 format (AB 2 projects are Brightway 2.4 format, which is a separate question, see "Open questions").
- Competition risk: AB 3 already has a contribution tree. Your differentiators should be the things it lacks (see section 4): SimaPro-like user-defined grouping, side-by-side comparison, process-level detail panels, shareable or exportable views, and a faster or richer UI. If those are not the plan, consider contributing to AB's tree instead.

"Both" is only worth it later, and only cheaply: because AB already hosts QtWebEngine pages, a thin AB launcher or tab that opens `http://127.0.0.1:<port>` of your app in a QWebEngineView would be a few dozen lines once AB 3's plugin API is settled. Revisit when AB 3 is stable and has a documented plugin API.

## 2. Plugin system

### AB 2.x (stable, `main` branch)
- Introduced in 2.8.0; designed by Rémy Le Calloch. Source: [Plugins wiki](https://github.com/LCA-ActivityBrowser/activity-browser/wiki/Plugins).
- **Discovery:** not entry points. `PluginController.discover_plugins()` iterates `pkgutil.iter_modules()` and picks any importable module whose name starts with `ab_plugin`; it imports it and instantiates `plugin_lib.Plugin()`. Source: [`controllers/plugin.py` on main](https://github.com/LCA-ActivityBrowser/activity-browser/blob/main/activity_browser/controllers/plugin.py).
- **API:** subclass `activity_browser.plugin.Plugin` with `load()`, `close()`, `remove()`; the plugin exposes `infos` (name etc.) and a `tabs` list of `PluginTab` (a `QTabWidget` subclass, PySide2) that AB adds to the left or right panel. Enabled per project via `Tools > Plugins`. Source: [`plugin.py`](https://github.com/LCA-ActivityBrowser/activity-browser/blob/main/activity_browser/plugin.py), [`layouts/tabs/plugin.py`](https://github.com/LCA-ActivityBrowser/activity-browser/blob/main/activity_browser/layouts/tabs/plugin.py).
- **Distribution:** mainly conda (personal channels, e.g. `conda install -c pan6ora -c conda-forge ab-plugin-notebook`); some also on PyPI. Plugin template: [activity-browser-plugin-template](https://github.com/Pan6ora/activity-browser-plugin-template). Wiki warns: "The plugin system is still in development so keep in mind that things may change at any point."
- **Known plugins** (wiki list, all third-party, unverified by AB team): [ScenarioLink](https://github.com/polca/ScenarioLink) (premise/unfold scenario databases; PyPI `ab-plugin-scenariolink` 0.1.0 requires `activity-browser>=2.10.1`), [ReSICLED](https://github.com/Pan6ora/ab-plugin-ReSICLED), [Notebook](https://github.com/Pan6ora/ab-plugin-Notebook), template. Source: [Plugins wiki](https://github.com/LCA-ActivityBrowser/activity-browser/wiki/Plugins).

### AB 3 (beta)
- The AB 2 plugin controller, `Plugin` base class and `PluginTab` are **removed** from the `beta` tree (no `plugin.py`, no `controllers/`). I confirmed by listing the tree; there is no file named like a plugin API apart from the settings page.
- What exists: a Settings chapter "Plugins" ([`app/pages/settings/plugins.py`](https://github.com/LCA-ActivityBrowser/activity-browser/blob/beta/activity_browser/app/pages/settings/plugins.py)) where the user types Python package names; `__main__.load_plugins()` just does `__import__(name)` for each at startup ([`__main__.py`](https://github.com/LCA-ActivityBrowser/activity-browser/blob/beta/activity_browser/__main__.py)). A signal `plugin_selected` is left over in `signalling.py`. There is no registration API, no tab-injection contract and no entry points. A package could in principle import `activity_browser.app` (`app.main_window`, `app.signals`, `app.settings`) and add a widget itself, but that is an undocumented internal surface.
- Maintainers' statement in [`AGENTS.md`](https://github.com/LCA-ActivityBrowser/activity-browser/blob/beta/AGENTS.md): "Plugin architecture is being redesigned. Do not harden or invent a plugin API contract here."
- Wiki and README still point to the AB 2 plugin page. **[UNVERIFIED]** whether the existing AB 2 plugins (ScenarioLink etc.) work on AB 3; given the removal of `Plugin`/`PluginTab` and the PySide2 to PySide6 move, assume not.
- API change AB 2 to AB 3: **effectively removed**, replacement not yet designed.

## 3. Web views inside AB

- **Yes, QtWebEngine is used.** `qt-webengine` is in the conda recipe, `application.py` sets `QTWEBENGINE_CHROMIUM_FLAGS`, and there is a `QWebEnginePage` subclass (`ABWebEnginePage`) in `ui/widgets/web_engine_page.py`. Sources: [`recipe/meta.yaml` (main)](https://github.com/LCA-ActivityBrowser/activity-browser/blob/main/recipe/meta.yaml), [`web_engine_page.py` (beta)](https://github.com/LCA-ActivityBrowser/activity-browser/blob/beta/activity_browser/ui/widgets/web_engine_page.py).
- Features rendered as HTML/JS in WebEngine (AB 3 `static/`): Sankey navigator, Graph Explorer, activity graph, and the new contribution-tree D3 plot. D3 7.9 and dagre-d3-es are vendored (ADR [0006](https://github.com/LCA-ActivityBrowser/activity-browser/blob/beta/docs/adr/0006-d3-7-dagre-d3-es.md)). Python-JS communication uses `QWebChannel` (`ContributionTreeD3Bridge` in [`contribution_tree_d3_plot.py`](https://github.com/LCA-ActivityBrowser/activity-browser/blob/beta/activity_browser/app/pages/lca_results/contribution_tree_d3_plot.py)).
- Feasibility of embedding your own web UI: **technically yes** (a `QWebEngineView` loading `http://127.0.0.1:port` or `file://` is straightforward since WebEngine is already a hard dependency), but with no stable plugin hook (section 2) the embedding point is fragile. Note AB disables the Chromium sandbox or GPU in some environments, which can affect heavy React UIs. **[UNVERIFIED]** performance of a large React tree inside AB's pinned PySide6 (<6.10) WebEngine.
- Note that AB's own web views are small, embedded, Python-driven D3 pages, not a client/server web app; a FastAPI backend inside the AB process would need its own thread/event loop (not checked).

### Gap analysis for a SimaPro-like viewer (what nobody provides yet)
- User-defined **grouping of processes** (by arbitrary rule, saved with the project) applied to the tree and charts, rather than AB's plot-only sibling aggregation by one metadata field.
- A **standalone, browser-based** explorer that reads an existing Brightway project (no Qt, no conda-only distribution), shareable screenshots or HTML export.
- Side-by-side **comparison** of products/scenarios in one tree; multi-impact-category columns (SimaPro "network" view equivalents). **[UNVERIFIED]** whether AB 3's tree does multi-category.
- Stable maintained API layer (FastAPI) over `bw_graph_tools` + `bw2calc` for other front ends.

## Open questions / things not verified
- Whether an AB 3 beta project (Brightway 2.5 format) can be opened read-only by a separate process while AB is running (SQLite locking). Not tested.
- Whether AB 2 (Brightway 2.4) projects are readable with bw2data 4.7 without migration. Brightway docs say 4.x is only compatible with Brightway 2.5 ([bw2data changelog](https://pypi.org/project/bw2data/)); a standalone app must decide how to handle 2.4 projects (probably require a 2.5 project).
- AB 3 stable release date and the future plugin API design: no public roadmap found.
- Exact AB 3 beta runtime pins vs. bw2calc 2.5.0 / bw2data 4.7 (their CI was not inspected).
- Licence of AB: LGPLv3+ (from PyPI classifiers), which matters if you copy code from AB's contribution tree.
